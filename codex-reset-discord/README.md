# 개인 Discord용 Codex 리셋 알림 프로토타입

리셋 예고, 리셋 완료, 초기화권 지급 안내만 보내는 Python 3.11+ 프로그램입니다. Python 표준 라이브러리만 사용합니다. AI API 비용은 없습니다. 실제 Discord 서버나 GitHub 저장소는 아직 생성/연결하지 않았습니다.

## 봇과 웹훅 중 무엇을 쓰나요?

| 항목 | Discord 봇/앱 | 채널에 보내는 웹훅 |
|---|---|---|
| 용도 | 명령어, 버튼, 대화, 역할/서버 기능 | 정해진 채널에 자동 공지 게시 |
| 초기 설정 | 앱 등록, 권한, 설치와 토큰 관리 | 채널에 웹훅 생성 |
| 글의 판단/번역 | 별도 프로그램이나 AI가 담당 | 역시 별도 프로그램이나 AI가 담당 |
| 실행 환경 | 기능에 따라 상시 연결 또는 HTTP 실행 환경 | 공지 전송 시에만 실행 가능 |
| 이번 프로토타입 | 추후 `/최근리셋` 등의 기능에 적합 | **현재 채택** |

봇이 곧 AI라는 뜻은 아닙니다. 웹훅에도 AI가 작성한 공지를 보낼 수 있습니다. 반대로 봇도 고정 규칙으로만 동작할 수 있습니다. 이번에는 한 채널에 공지를 보내는 일이 전부이므로 웹훅이면 충분합니다. 나중에 다른 서비스도 별도 채널/웹훅으로 추가할 수 있습니다.

Discord의 **받는 웹훅**은 공지를 넣는 주소입니다. 데이터 제공자가 새 글을 알려주는 **보내는 웹훅/구독 기능**과 다릅니다. Discord 웹훅을 만들었다고 데이터 제공자가 그 주소로 자동 연락하지는 않습니다.

## 동작 흐름과 확인 주기

```text
GitHub가 10분마다 임시 실행 환경 시작
  → Codex Reset의 timeline/feed JSON 조회
  → 오래된 응답/알 수 없는 형식 차단
  → 세 가지 유형으로 보수적 분류
  → 저장된 ID·단계와 비교
  → 새 알림만 Discord 웹훅으로 게시
  → 전송 기록을 GitHub 저장소에 저장하고 종료
```

- 매시 03/13/23/33/43/53분에 확인하도록 구성했습니다. 정각 한 번이 아닙니다.
- 아무 소식이 없으면 Discord 메시지를 보내지 않습니다. 확인 요청만 두 번 실행합니다.
- 직접 상시 서버를 켜두지 않습니다. 각 작업 때 GitHub가 컴퓨터를 잠깐 제공하고 종료합니다. Discord 서버 자체를 사용자의 PC에서 운영하는 것도 아닙니다.
- 전달까지는 **원문 → 제공 사이트 반영 지연 + 다음 확인까지 최대 약 10분 + GitHub 실행 지연**이 걸릴 수 있습니다. 10분 이내 수신을 보장하지 않습니다.
- GitHub 예약 실행은 최단 5분입니다. 바쁜 시간에는 지연되거나 실행이 빠질 수 있습니다. 공개 저장소는 60일간 저장소 활동이 없으면 예약이 중지될 수 있습니다.
- 원문/이벤트의 갱신 시각이 60분보다 오래되거나 제공자가 `stale`로 표시하면 알림을 보내지 않고 실패를 표시합니다. 새 글이 오랫동안 없는 것과 피드 자체가 갱신되지 않은 것은 구분합니다.

## 신호가 올 때만 확인하면 안 되나요?

제공자가 외부 소비자에게 webhook/WebSub/SSE 등의 새 이벤트를 전달하는 인터페이스를 제공하면 가능합니다. 확인한 공개 개발자 문서에는 REST 조회와 MCP가 있으며, 외부 알림 구독 등록 API는 문서화되어 있지 않습니다. 여기의 MCP `Streamable HTTP`는 새 공지가 생길 때 알려주는 구독 기능을 뜻하지 않습니다. 따라서 현재 프로토타입은 폴링합니다.

Atom/RSS 피드도 일반적으로 조회가 필요하며, Discord 웹훅만으로 수집 주기를 없앨 수 없습니다. 나중에 공급자가 이벤트 구독을 제공하면 수집 부분만 바꾸고 분류·Discord 전송 코드는 재사용할 수 있습니다.

## GitHub와 GitHub Actions는 각각 무엇을 하나요?

1. **저장소:** Python 코드, 실행 설정, 보낸 이벤트 ID/단계를 저장합니다.
2. **Actions:** 정해진 시간에 코드를 실행합니다. 수동 실행과 실패 로그도 제공합니다.
3. **Secrets:** `DISCORD_WEBHOOK_URL`을 비공개 환경 변수로 전달합니다.
4. **상태 저장:** 실행 환경의 디스크는 다음 실행에 유지되지 않으므로 `state/state.json`을 Git 커밋으로 남깁니다. 이 파일에는 시각과 이벤트 ID만 있고 웹훅 비밀값은 없습니다.

공개 저장소의 표준 GitHub-hosted runner는 현재 무료입니다. 비공개 저장소는 무료 실행량이 정해져 있어 10분 간격의 월간 실행이 무료 한도를 넘을 수 있습니다. 무료가 우선이라면 코드와 비밀이 아닌 상태만 공개하고, 웹훅은 Secrets에 보관하는 구성을 권합니다. 공개 저장소에 프로그램을 올리는 것과 Discord 서버를 공개하는 것은 별개입니다.

상태 커밋에 쓰기 권한이 필요합니다. 저장소의 Actions 쓰기 제한이나 브랜치 보호 규칙이 직접 커밋을 막으면 설정을 검토해야 합니다. 다른 운영 코드가 없는 전용 개인 저장소에서 시작하는 편이 간단합니다. 이 예시는 상태를 기본 브랜치에만 저장하며 별도 데이터베이스는 사용하지 않습니다.

## 세 가지 유형의 실제 판단 기준

| 유형 | 근거와 조건 | 한국어 알림 |
|---|---|---|
| 리셋 예고 | 서비스의 `group=reset`, `announcement_state=none` + 전체/사용량 리셋과 미래 시점을 명시한 영어 문장. 부정/조건/의문/모호한 표현 제외 | 전체 리셋 예고, 아직 완료 미확인 |
| 리셋 완료 | 서비스가 문서화한 완료 기준 `group=reset`, `announcement_state=announced` | **추적 서비스 기준** 전체 리셋 완료 |
| 초기화권 지급 | `group=credits` + banked reset 명시 + 제공자의 지급 상태 또는 명시적 지급 문구 | 지급 안내/진행/확인을 구분 |

- X를 직접 수집하지 않습니다. 커뮤니티 추적 서비스가 수집·정리한 데이터에 의존합니다.
- 서비스의 `group=reset`만으로 완료라고 판단하지 않습니다. 실제 응답에 리셋 관련 댓글과 농담도 그 그룹으로 들어 있었습니다.
- 원문의 `kind`, LLM 내부 분류, 확률 점수는 사용하지 않습니다. 알려진 데이터와 보수적 규칙을 사용하며, 알 수 없는 유형은 전송하지 않습니다.
- 애매한 힌트를 놓칠 수 있습니다. 초기 버전은 오탐을 줄이는 쪽을 택했습니다. 사이트 자체의 분류 오류나 수집 누락을 독립적으로 검증하지는 못합니다.
- 완료는 본인의 계정 상태를 직접 조회한 결과가 아닙니다. 초기화권도 본인에게 실제 지급됐는지는 계정에서 확인해야 합니다.
- 같은 이벤트가 예고에서 완료로 바뀌면 새 알림을 보냅니다. 초기화권도 같은 항목의 지급 단계가 바뀌면 새 알림을 보냅니다.
- 다른 게시물 ID로 반복 공지된 동일 사건은 두 번 올라올 수 있습니다. 현재 중복 방지는 **이벤트 ID + 유형 + 단계** 기준입니다.

## 한글 번역은 어디까지 되나요?

현재 버전은 세 유형의 **정형 한국어 요약**을 생성하고 영어 근거와 관련 X 링크를 함께 붙입니다. 원문 전체를 문장별로 자동 번역하지 않습니다. timeline에 서비스가 작성한 영어 요약만 있으면 그것을 원문인 것처럼 표시하지 않고, 피드에서 같은 ID의 실제 원문이 확인되면 `Tibo 영어 원문`으로 표시합니다.

게시/기록 시각은 한국 시간으로 표시합니다. 이는 적용 예정 시각과 다릅니다. 원문의 tomorrow/EOD/PST 등은 게시자 기준이며, 태평양 표준시·서머타임을 혼용할 수 있어 이 버전은 예정 시각을 추측해서 확정하지 않습니다. 적용 시각·대상 요금제의 상세 내용은 영어 근거/원문에서 확인해야 합니다.

원문 전체의 자연스러운 한국어 번역이 필요하면 추후 번역 모듈을 붙일 수 있습니다. AI를 붙일 경우 **판단 근거를 가진 공지만 번역에 넘기고, AI가 확인되지 않은 글을 완료로 승격하지 못하게** 하는 방향을 권합니다. 별도 AI API의 요금이나 로컬 모델 실행 환경은 이 프로토타입에 포함하지 않습니다.

## 로컬 미리보기 (외부 전송 없음)

이 폴더에서 Python 3.11 이상으로 실행합니다. 패키지 설치는 필요 없습니다.

```powershell
python -m unittest discover -v
python -m py_compile monitor.py test_monitor.py
python monitor.py --demo
```

`--demo`는 가상 데이터로 세 가지 메시지를 출력합니다. `examples/demo-messages.json`에도 같은 출력이 있습니다. 데모를 실제 Discord로 보내는 기능은 없습니다.

실제 공개 API를 읽되 전송/상태 저장을 하지 않는 미리보기:

```powershell
python monitor.py
```

기본 실행도 미리보기입니다. 운영 공지는 `--send`를 명시해야 전송됩니다. 온라인 미리보기는 최근 이력의 분류 결과도 보여 주며, 현재 전송 대기 목록이라는 뜻은 아닙니다.

`DISCORD_WEBHOOK_URL`이 연결된 환경에서 `python monitor.py --test-webhook`을 실행하면, 실제 리셋 소식이 아님을 명시한 연결 테스트 메시지 **1건**만 Discord에 전송합니다. 공개 API를 조회하거나 중복 방지 상태를 변경하지 않습니다. GitHub에서는 아래 `test` 모드로 실행할 수 있습니다.

## Discord와 GitHub 연결 순서

1. Discord에서 개인 서버를 만들고 텍스트 채널 `codex-알림`을 만듭니다. 나중에 다른 서비스용 채널을 추가하면 됩니다.
2. PC/웹 Discord의 서버 설정 → 연동(Integrations) → 웹훅 → 새 웹훅에서 대상 채널을 지정합니다. 웹훅 URL을 복사하되 채팅이나 공개 코드에 붙이지 않습니다.
3. GitHub에서 이 프로그램 전용 공개 저장소를 만듭니다. 이름은 예를 들어 `personal-discord-alerts`로 지정합니다. 압축을 풀고 `codex-reset-discord` 폴더의 **내용**을 저장소 루트에 넣습니다. GitHub의 Add file → Upload files에 폴더 안의 파일과 하위 폴더를 끌어 놓은 뒤 Commit changes 합니다. `codex-reset-discord` 폴더 자체가 저장소 안에 한 단계 더 들어가면 안 됩니다. `.github/workflows/codex-alerts.yml`도 포함해야 합니다. 웹에서 파일을 올릴 때 `.github` 폴더가 빠지지 않게 확인합니다.
4. 저장소 Settings → Secrets and variables → Actions → New repository secret에 이름 `DISCORD_WEBHOOK_URL`, 값 웹훅 URL을 저장합니다.
5. Actions 탭 → Codex Reset Alerts → Run workflow → 기본 브랜치를 선택하고 `preview`로 실행합니다. Run one check 단계에 분류 JSON이 출력되고 녹색으로 완료되면 공개 API 읽기가 정상입니다. 이 workflow는 기본 브랜치에서만 실행됩니다.
6. 같은 메뉴에서 `test`로 실행합니다. Discord에 `🧪 연결 테스트 · 실제 리셋 소식이 아닙니다` 메시지가 1건 올라오면 GitHub → Discord 게시 연결이 정상입니다. 휴대폰 알림도 확인합니다. 이 테스트는 리셋 이력에 영향을 주지 않습니다.
7. `send`로 수동 실행하면 최초 기준점만 저장하고 과거 공지는 전송하지 않습니다. 최초 운영 실행의 `initialized: true`, `sent: 0`은 정상입니다. 이후 새 항목부터 전송합니다. 예약 실행이 먼저 기준점을 저장했거나 새 항목이 없으면 수동 `send`에서도 전송 건수가 0일 수 있습니다.
8. 예약 실행은 기본 브랜치에 workflow 파일이 올라가면 활성화됩니다. Secrets 설정 전 예약이 먼저 실행되면 비밀값 누락 오류로 종료할 뿐 외부 전송은 하지 않습니다.
9. Discord 채널의 모든 메시지 알림, 서버 모바일 푸시, 휴대폰 Discord 알림 허용을 설정합니다. 휴대폰 알림 검증 시 Discord 앱을 닫고 다시 `test`를 실행해 확인하세요.

연결 후 **preview 성공 → test 메시지 수신 → send 기준점 저장**까지 확인하면 초기 연결 검증이 끝납니다. 실제 새 리셋 이벤트의 자동 수신은 해당 이벤트가 발생했을 때 별도로 확인합니다. 시험을 멈추려면 Actions → Codex Reset Alerts의 메뉴에서 Disable workflow를 선택하고, 다시 시작할 때 Enable workflow로 복구합니다.

03분부터 시작하는 이유는 정각의 GitHub 예약 작업 혼잡을 피하기 위해서입니다. 03이라는 숫자 자체에 특별한 의미는 없습니다. 10분 간격을 유지하는 02/12/22/32/42/52분 등으로 바꿔도 됩니다. 예약 시각대로 반드시 즉시 실행되는 것은 아닙니다.

실제 전송을 시작하는 순간부터 외부 Discord 채널에 글이 게시됩니다. 현재 전달 파일은 로컬 검증만 했으며, 사용자의 서버에 전송하지 않았습니다.

## 신뢰성 범위와 실패 처리

- 처음에는 기존 분류 항목을 기준점으로 저장하고 공지를 보내지 않습니다. 이후 24시간 이내의 새 항목/단계 변경을 전송합니다. 24시간보다 오래된 누락은 자동 재전송하지 않습니다.
- Discord가 메시지 ID로 성공을 확인한 후에만 상태에 기록합니다. 여러 건 중 뒤의 전송이 실패해도 앞의 성공 기록은 저장하도록 workflow를 구성했습니다.
- API나 Discord의 HTTP 오류·429에서 같은 실행 안의 공격적인 재시도는 하지 않습니다. 429의 `Retry-After`(초 또는 HTTP 날짜)는 `state/cooldown.json`에 저장해 해당 시간이 지나기 전 예약 실행도 건너뜁니다. 값이 없거나 읽을 수 없으면 10분 대기합니다. API는 문서대로 최대 1분당 1회보다 느리게 조회합니다.
- 네트워크 응답 유실이나 상태 커밋/푸시 실패가 발생하면, 전송은 되었으나 기록이 없어서 드물게 중복 게시될 수 있습니다. webhook 전송과 Git 상태 저장을 원자적으로 묶을 수 없어 정확히 한 번의 전송은 보장하지 않습니다.
- 상태 파일이 손상되면 조용히 초기화하지 않고 중단합니다. GitHub의 실패 로그를 확인하세요. 실패 자체를 Discord로 보내는 별도 모니터는 포함하지 않았습니다.
- 외부 글의 멘션을 무력화하고 `allowed_mentions`를 비워 @everyone 같은 예상하지 못한 알림을 방지합니다. 외부 글은 프로그램 지시로 실행하지 않습니다.
